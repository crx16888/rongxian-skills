# Frontend Product Review

## 使用边界

使用本 skill 处理：

- 用户让你看一个 Web 产品、后台系统、B 端页面、前端 Demo 或交互流程。
- 用户要求“给修改建议”“规划怎么改”“页面怎么设计”“点击之后会怎么样”。
- 用户不满意抽象建议，希望具体到页面每个区域、每个入口、每个按钮和点击结果。

不要只输出“优化信息架构”“强化用户路径”“提升可用性”这类抽象判断。每条建议都要落到用户能想象的页面变化。

## 工作流

1. 先判断主路径：普通用户从哪里开始，看什么，点哪里，最后完成什么。
2. 再拆页面区域：导航、顶部、筛选、列表、卡片、侧板、弹窗、详情页、空状态。
3. 对每个区域写清楚：保留什么、改什么、删除或降级什么。
4. 对关键点击写清楚：点击前看到什么，点击后打开哪里，页面状态怎么变，下一步按钮是什么。
5. 区分普通用户路径和管理者路径。
6. 如果有“入口重复”，明确哪个入口是主入口，哪个入口降级为筛选、抽屉或管理总览。

## 默认输出结构

按任务复杂度压缩或展开，但必须包含这些信息：

```text
总目标
1. 导航怎么改
2. 页面顶部怎么改
3. 筛选区怎么改
4. 列表/主内容区怎么改
5. 点击关键状态/按钮后会发生什么
6. 右侧抽屉/弹窗/详情页怎么改
7. 管理入口或汇总页怎么改
8. 普通用户最终路径
9. 管理者最终路径
```

## 写法要求

- 用朴素中文，不堆技术词。
- 每一段都回答“页面上会变成什么”和“用户点了之后发生什么”。
- 按页面区域讲，不按代码文件讲，除非用户明确要工程实现计划。
- 按按钮真实文案写，例如“去补字段”“看阻断原因”“处理逾期”，不要统一写“查看详情”。
- 对保留、降级、删除说清楚，不含糊。
- 如果涉及 B 端流程，优先讲“谁处理、在哪里看、点哪里、系统怎么反馈”。

## 质量检查

输出前检查：

- 是否具体到了页面顶部、筛选区、列表、按钮、侧板或弹窗。
- 是否写清关键点击后的结果。
- 是否明确普通用户和管理者的路径。
- 是否避免了只有原则、没有页面变化的空话。
- 是否用用户能听懂的语言表达。
